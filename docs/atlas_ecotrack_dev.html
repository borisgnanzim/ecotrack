EcoTrack, de la poubelle connectée au tableau de bord

Une plateforme qui suit le remplissage de conteneurs de déchets grâce à des capteurs, optimise les tournées de collecte et implique les citoyens. Cette version ne garde que ce qui concerne les développeurs : ce que l'école demande à la spécialité Développement, ce que nos dossiers et soutenances des blocs 1 et 2 ont décrit, ce que le code fait réellement, et l'inventaire de ce qu'il reste à faire pour les blocs 3 et 4.

Le sujet

Une collecte guidée par les données

Aujourd'hui les camions suivent des circuits fixes et s'arrêtent devant des conteneurs vides. Des capteurs mesurent le remplissage, la plateforme décide quels conteneurs vider et dans quel ordre.

Le cadre

Un projet sur deux ans

En M1 (janvier à juin 2026), nous avons construit la plateforme : blocs RNCP 1 et 2. En M2 (octobre 2026 à juin 2027), nous devons l'exploiter comme si elle était en production : blocs 3 et 4.

Ce qui existe

7 services, 2 fronts, une chaîne IoT

Une API Gateway, six microservices Node.js/Express (Prisma, une base PostgreSQL chacun), Kafka et Redis en Docker, un simulateur de capteurs en Python, et deux applications Vue 3 (admin et citoyen).

Le point d'attention

Le back est en avance sur le front

L'analytics, la gamification, les notifications et le temps réel existent côté serveur mais aucune interface ne les appelle. Plusieurs affirmations des dossiers et soutenances de juin ne correspondent pas au code (voir Dossiers et code).

Cette semaine compte. Le jalon Développement du 26 au 30 octobre 2026 (module Architecture Microservices) est le Sprint 0 de la V2 : audit de notre V1 et plan de décomposition. Cette page en est une base.

Le calcul de rentabilité du dossier Bloc 1

Ces chiffres reposent sur des hypothèses, pas sur des mesures. La base de 2 000 000 € vient des notes de la soutenance : 50 agents × 200 €/jour × 200 jours/an. Le tableau détaillé du dossier donne :

Collecte : 2 000 000 € × 15 % = 300 000 €/an · Carburant : 200 000 € × 20 % = 40 000 €/an
Productivité : 500 000 € × 10 % = 50 000 €/an · Débordements urgents évités : 20 000 €/an
Gains : 300 000 + 40 000 + 50 000 + 20 000 = 410 000 €/an
Coût sur 3 ans (TCO) : 144 000 (développement) + 16 560 (infrastructure) + 86 400 (maintenance) = 246 960 €
Rentabilité : 178 320 € investis l'an 1 ÷ (410 000 ÷ 12 = 34 167 €/mois) = 5,2 mois → atteinte au 6ᵉ mois

Trois versions coexistent. Le résumé du même dossier annonce un TCO de 161 200 € et 390 000 € de gains ; l'oral passait par 2 000 000 € × 20 % × 75 % = 300 000 €. Il faut en garder une seule, la version détaillée ci-dessus, avant de la réutiliser pour l'appel d'offre de la V2.

Le volume de mesures, selon les hypothèses

Les documents ne partent pas tous de la même fréquence d'envoi. Le calcul change beaucoup :

CDC commun (1 mesure / 15 min) : 2 000 ÷ 15 = 133 msg/min ≈ 2,2 msg/s
Dossier BC1 (1 mesure / min) : 2 000 ÷ 60 s = 33 msg/s · 2 000 × 60 × 24 × 365 ≈ 1,05 milliard/an
Notre simulateur (1 mesure / 300 s) : 2 000 ÷ 300 = 6,7 msg/s · en V2 : 5 000 ÷ 300 = 16,7 msg/s

L'exigence « 400 msg/min » (6,7 msg/s) correspond exactement à 2 000 capteurs toutes les 5 minutes, soit le réglage par défaut du simulateur.

Le CDC M1 décrit une stack très précise (React, Sequelize, Joi…). Le professeur référent a fixé un cadre plus simple : c'est un projet d'école, et ce qui compte, c'est que nous sachions expliquer ce que nous avons fait.

Critère 1

Un framework Vue

Les deux fronts sont en Vue 3 avec Vite. Le choix est justifié par la veille du BC1 (Vue 43/50, prise en main plus rapide que React pour une équipe de trois).

Critère 2

Que ça passe bien

Les parcours principaux fonctionnent de bout en bout. Quelques liaisons entre services restent à réparer (voir le trajet d'une mesure).

Critère 3

Que ce soit soutenable

Défendable à l'oral : tout ce qu'on montre doit marcher, et chacun doit pouvoir l'expliquer. On n'annonce pas ce qui n'existe pas (voir Dossiers et code).

Suivre une donnée

Le trajet d'une mesure, du capteur à l'écran

C'est le flux 1 du cahier des charges (« capteur → tableau de bord »). En le suivant dans le code, on voit où il s'arrête.

1

Le simulateur publie

sensor_simulator.py envoie toutes les 300 s, pour chaque conteneur, fillLevel, température et humidité sur le topic MQTT containers/<id>/data. Le remplissage monte de 0 à 5 points par envoi et repart entre 5 et 15 % à 100 %.

2

service-iot reçoit et contrôle

Il vérifie que le remplissage est entre 0 et 100, repère les anomalies (température hors de −10 à 60 °C, humidité hors de 0 à 100 %), enregistre la mesure et crée une alerte si le remplissage dépasse 90 %.

3

Kafka diffuse

La mesure part sur le topic container-fill-level. service-routes et service-analytics y sont abonnés.

4

service-containers n'écoute pas

Il publie sur Kafka mais n'a aucun consommateur : son fillLevel n'est mis à jour que par POST /containers/:id/fill-history. La carte de l'admin ne voit donc pas les mesures des capteurs.

5

Le temps réel n'atteint pas l'écran

service-containers émet fill_level_updated et critical_alert par Socket.io, mais aucun front n'a de client Socket.io. L'écran se met à jour au rechargement.

6

La gamification n'entend rien

Elle attend des topics nommés container-events.container-fill-level-updated, iot-events.… : des noms que personne ne publie.

À retenir : chaque maillon fonctionne seul ; ce sont les liaisons entre services qui manquent. C'est la priorité d'une refonte, avant d'ajouter des fonctionnalités.

Pratique

Lancer le projet en local

D'après le Makefile, les notes « Commandes lancement back » et les README. PostgreSQL doit tourner sur la machine, car il est commenté dans le compose.

# 1. Infrastructure : Kafka, Zookeeper, Redis (+ Kafka UI :8080, Redis Commander :8081)
make up
make kafka-create-topics

# 2. Chaque service : dépendances, client Prisma, migrations, démarrage
cd backend/service-containers
npm install
npx prisma generate
npx prisma migrate dev
npm run dev            # ou npm run pm2:start (clustering PM2)

# 3. Capteurs simulés (Python + paho-mqtt, broker MQTT requis)
python backend/service-iot/simulator/sensor_simulator.py

# 4. Fronts
cd front/ecotrack-admin-vjs   && npm install && npm run dev   # :5173
cd front/ecotrack-citoyen-vjs && npm install && npm run dev   # :5174

Documentation Swagger de chaque service : /api-docs (et /docs pour routes). Variable clé des fronts : VITE_APP_BACK_API_GATEWAY, absente du .env.example citoyen.

Vocabulaire

Glossaire

API Gateway
Point d'entrée unique : reçoit toutes les requêtes des fronts et les transmet au bon service.
Microservice
Petite application autonome avec sa propre base, déployable sans toucher aux autres.
MQTT
Protocole léger pour objets connectés : un capteur publie sur un « topic », un broker le transmet aux abonnés.
Kafka
Bus de messages durable : un service publie un événement, d'autres le consomment sans se connaître.
Topic
Nom du canal sur lequel circulent les messages (MQTT ou Kafka). Deux services doivent utiliser exactement le même nom.
Prisma
ORM : décrit les tables dans schema.prisma, génère les migrations et le code d'accès à la base.
PostGIS
Extension géographique de PostgreSQL (distances, polygones, index spatiaux).
TSP · 2-opt
Problème du voyageur de commerce : trouver l'ordre de passage le plus court. 2-opt améliore un trajet en inversant des portions.
JWT · RBAC
Jeton signé qui prouve l'identité ; contrôle d'accès selon le rôle.
Socket.io
Connexion permanente qui permet au serveur de pousser une information au navigateur.
Choroplèthe
Carte où chaque zone est colorée selon une valeur (remplissage moyen, par exemple).
RNCP · Bloc
Certification nationale découpée en blocs de compétences, évalués séparément.
Sprint 0
Première itération de la V2 : audit du V1 et remise à niveau avant toute nouvelle fonctionnalité.
RTO · RPO
Temps maximal pour redémarrer après une panne ; quantité maximale de données qu'on accepte de perdre.
