Avant de commencer

Comprendre le modèle C4

Le modèle C4, créé par Simon Brown, décrit l'architecture d'un logiciel en quatre niveaux de zoom, comme une carte qu'on agrandit : le pays, puis la ville, puis le quartier, puis le plan d'un bâtiment. Chaque niveau répond à une question différente et s'adresse à un public différent. Le nom vient des quatre niveaux : Contexte, Conteneurs, Composants, Code.

Les définitions à connaître

Personne
Un humain qui utilise le système : citoyen, agent, gestionnaire, administrateur.
Système logiciel
Le plus haut niveau : ce qui apporte de la valeur à ses utilisateurs et qu'une équipe possède. EcoTrack est notre système logiciel.
Système externe
Un système dont on dépend mais qu'on ne développe pas : OpenStreetMap, le serveur e-mail, les capteurs.
Conteneur
Une application ou un stockage qui doit tourner pour que le système fonctionne : une application web, un service, une base, un bus de messages. Ce n'est pas forcément un conteneur Docker, même si chez nous beaucoup peuvent l'être.
Composant
Un regroupement de code à l'intérieur d'un conteneur, avec une responsabilité claire et une interface : un contrôleur, un service métier, un repository. Un composant ne se déploie pas seul.
Code
Les éléments concrets qui réalisent un composant : classes, fonctions, modules, modèles de données.
Relation
Une flèche entre deux éléments. Elle porte toujours un verbe (« envoie », « lit et écrit ») et, à partir du C2, la technologie (HTTP, MQTT, Kafka, SQL).
Frontière
Le cadre en pointillés qui délimite ce qui est à l'intérieur de l'élément qu'on a ouvert : le système au C2, le conteneur au C3.

La différence entre les niveaux, en une phrase chacun

PassageCe qui changeExemple chez nous
C1 → C2La boîte « système » s'ouvre et devient plusieurs programmes qui tournent séparément« EcoTrack » devient les fronts, la gateway, les services, les bases
C2 → C3Un seul conteneur s'ouvre et devient des blocs de code qui tournent dans le même processus« service-routes » devient routeur, contrôleur, service, repository, optimiseur…
C3 → C4Un composant s'ouvre et devient ses classes, fonctions et tables« Optimizer » devient distance(), nearestNeighbor(), twoOpt()

Le test pour ne pas confondre conteneur et composant : peut-on le démarrer ou l'arrêter seul ? Si oui (service-routes, la base, Kafka), c'est un conteneur. Si non, parce qu'il vit dans le même programme qu'autre chose (RouteController, Optimizer), c'est un composant.

Ce qu'on montre au jury : le C1 et le C2 toujours ; le C3 pour un conteneur important ; le C4 rarement, seulement pour expliquer un point précis comme un algorithme. Plus on zoome, plus le schéma vieillit vite quand le code change.

Ce que le schéma met en évidence

La gamification est isolée

Elle n'est pas déclarée dans la gateway, donc les fronts ne peuvent pas l'appeler par le point d'entrée unique, et elle écoute des topics Kafka (container-events.…) que personne ne publie.

Les capteurs n'atteignent pas la carte

service-iot publie container-fill-level, mais service-containers ne le consomme pas : le remplissage affiché ne vient que de POST /containers/:id/fill-history.

Le temps réel s'arrête au serveur

service-containers émet ses alertes en Socket.io, mais aucun des deux fronts n'a de client Socket.io. C'est pourquoi aucune flèche ne remonte vers les fronts.

Deux services sur le port 3015

La gateway envoie /iot vers :3015, et le .env.example de la gamification utilise aussi 3015. Il faudra un seul tableau des ports.

Différences avec le C4 du dossier BC1 : le dossier montrait une gateway sur :3000, cinq services sur :3001 à :3005, une seule base PostgreSQL + PostGIS partagée et Kafka en mode KRaft avec les topics iot-data et alerts. Ces schémas-ci montrent le code tel qu'il est : sept services derrière les ports 3010 à 3015, une base par service sans PostGIS, Kafka avec Zookeeper. Pour la soutenance, ce sont eux qu'il faut présenter.

Le chemin d'une requête « optimiser une tournée »

  1. Le front admin envoie POST /routes/:id/optimize à la gateway, qui le transmet au routeur de service-routes.
  2. authMiddleware vérifie le jeton, puis roleMiddleware vérifie que l'utilisateur est admin ou manager.
  3. RouteController.optimizeRoute appelle RouteService.optimize(id).
  4. Le service charge la tournée, ajoute les conteneurs critiques, appelle l'Optimizer, puis enregistre les nouvelles étapes par le repository.
  5. Le contrôleur renvoie la tournée avec la distance avant, après et le gain.

Ce que le C3 met en évidence

Un contrat Kafka corrigé le 28/10/2026

service-iot publie { containerId, fillLevel }, mais l'abonné lisait fillPercentage : une tournée était créée pour presque chaque mesure. Il lit maintenant fillLevel et ignore les messages sans valeur numérique. Leçon : un nom de champ partagé entre deux services est un contrat à écrire noir sur blanc.

Le repository est contourné

L'abonné Kafka et RouteService.optimize appellent Prisma directement au lieu de passer par RouteRepository. Ça marche, mais l'accès aux données n'est plus centralisé.

Une copie des conteneurs non alimentée

La base du service a sa propre table containers, utilisée pour l'optimisation. Aucun abonnement à container-created ou container-updated ne la tient à jour.

Le contrôleur fait un peu trop

Il produit le PDF et l'e-mail lui-même. Ces deux appels pourraient passer par le service métier, pour garder le contrôleur limité au HTTP.

Niveau 4

C4 · Diagramme de code : l'optimisation des tournées

On ouvre le composant Optimizer et ce qu'il manipule. À ce niveau, on utilise un diagramme de classes UML : les modèles de données avec leurs attributs, les modules avec leurs fonctions publiques, et les liens entre eux.

Question

Comment ce composant est-il écrit ?

On y met

Classes ou modules, attributs, fonctions, associations et cardinalités

On n'y met pas

Tout le code du projet : un seul composant à la fois

Pour qui

Le développeur qui va modifier ce code

Lecture UML : « 1 » et « 0..* » indiquent combien d'objets sont liés (une tournée a zéro ou plusieurs étapes). Le losange plein signifie que les étapes appartiennent à la tournée et disparaissent avec elle. Les flèches en pointillés indiquent une dépendance « utilise ».

Ce que fait optimize(id), étape par étape

  1. Charge la tournée et la liste de ses conteneurs.
  2. Ajoute automatiquement tous les conteneurs dont le remplissage dépasse 80 %.
  3. Calcule la distance dans l'ordre d'origine, pour pouvoir comparer.
  4. Construit un premier ordre avec nearestNeighbor : depuis le point courant, aller toujours au conteneur le plus proche.
  5. L'améliore avec twoOpt : inverser une portion du trajet tant que cela raccourcit la distance totale (à partir de 4 conteneurs).
  6. Calcule la distance et le temps de chaque étape, remplace les anciennes étapes, puis renvoie le gain.

Les calculs utilisés

Distance entre deux conteneurs (formule de haversine, sur une Terre de rayon R = 6 371 km) :

x = sin²(Δlat / 2) + sin²(Δlon / 2) × cos(lat₁) × cos(lat₂) · distance = 2 × R × atan2(√x, √(1 − x))

Temps d'une étape : la distance divisée par 0,5 km/min (soit 30 km/h), plus 5 minutes d'arrêt. Exemple pour 3 km :

3 ÷ 0,5 + 5 = 6 + 5 = 11 minutes

Gain renvoyé au front. Exemple avec une tournée qui passe de 12,4 km à 9,8 km :

gain = (12,4 − 9,8) ÷ 12,4 × 100 = 2,6 ÷ 12,4 × 100 = 21,0 %

Les deux exemples sont illustratifs ; les valeurs réelles dépendent des coordonnées des conteneurs.

Soutenance

Le présenter en une minute

C1. EcoTrack sert quatre profils : le citoyen qui signale, l'agent qui collecte, le gestionnaire qui planifie et l'administrateur qui configure. Le système reçoit les mesures des capteurs en MQTT, s'appuie sur OpenStreetMap pour les cartes et envoie les feuilles de route par e-mail.
C2. Les deux applications Vue n'appellent qu'un seul point d'entrée, l'API Gateway, qui vérifie le jeton et redirige vers six microservices Express. Chaque service a sa propre base PostgreSQL. Les capteurs passent par un broker MQTT jusqu'au service IoT, qui publie le niveau de remplissage sur Kafka ; les services des tournées et des statistiques le consomment sans connaître l'émetteur.
C3. Dans le service des tournées, chaque requête traverse le routeur et les middlewares d'authentification, de rôle et de validation, puis le contrôleur, qui délègue au service métier. Le service s'appuie sur l'optimiseur pour l'ordre de passage et sur le repository pour la base. Les événements sortent par Kafka, le PDF par e-mail.
C4. Une tournée contient des étapes ordonnées, chacune liée à un conteneur. L'optimisation part du plus proche voisin, puis applique 2-opt, qui inverse des portions du trajet tant que la distance baisse. Les distances sont calculées avec la formule de haversine.
Question probable : « Pourquoi des microservices ? » Parce que l'IoT, les statistiques et les tournées n'ont pas la même charge : on peut les faire évoluer, tester et déployer séparément, au prix d'une infrastructure plus lourde (Kafka, une base par service).

Schémas établis à partir du code (routes, schémas Prisma, configuration de la gateway, abonnés Kafka, appels Axios des fronts) le 28 octobre 2026. À mettre à jour après chaque changement d'architecture.
